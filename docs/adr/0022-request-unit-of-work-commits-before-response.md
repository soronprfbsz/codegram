# 요청 단위 작업(unit of work)의 커밋은 응답 전송 **전**에 끝낸다

> **Status**: Accepted · **Tags**: `architecture` · **Date**: 2026-07-28 · **Supersedes**: — · **Related**: ADR-0006, ADR-0007

백엔드의 트랜잭션 경계는 그대로 **요청 스코프**다(서비스·리포지토리는 `flush()`만, 커밋은 요청 스코프가 소유 — ADR-0007 계층 규약). 다만 그 커밋이 **언제** 실행되는지를 못박는다: 커밋은 **응답이 클라이언트로 나가기 전에** 완료되어야 한다. 이를 위해 커밋만 별도 의존성 `commit_unit_of_work`로 떼어 `Depends(commit_unit_of_work, scope="function")`로 **앱 전역**에 건다. 세션 자체는 종전대로 요청당 하나(`get_session`)이고, 모든 주입 지점은 공용 별칭 `SessionDep` 하나만 쓴다(G1 단일 출처).

배경(왜 명시가 필요한가):

- FastAPI는 `yield` 의존성의 종료 코드를 실행할 시점을 **두 가지**로 제공한다. 기본값(`scope="request"`)은 종료 코드를 **응답 전송 이후**에 돌린다. 즉 `get_session`이 커밋하기 전에 이미 2xx가 나간다.
- 실측(2026-07-28, 로컬 스택): 커밋 직전에 500ms 지연을 넣어도 `DELETE .../snapshots/{id}`는 **9ms 만에 204**를 반환했다. 그리고 삭제 직후(약 4ms 뒤) 목록을 조회하면 **10회 중 10회** 삭제된 행이 그대로 보였다. 프로젝트 생성 직후 그 프로젝트에 스냅샷을 만들면 **404**가 났다 — 생성이 아직 커밋되지 않았기 때문이다.
- 이 창(window)은 밀리초 단위지만 **프론트가 변경 직후 재조회하는 것이 정상 패턴**(TanStack Query invalidate)이라 사실상 100% 재현된다. 사용자에겐 "삭제했는데 그대로다"로 보인다.
- 더 나쁜 쪽: 커밋이 응답보다 늦으면 **커밋 실패를 클라이언트에 알릴 방법이 없다.** 무결성 위반·연결 끊김으로 커밋이 실패해도 클라이언트는 이미 받은 2xx를 성공으로 믿는다. 쓰기 유실이 조용히 발생한다.

따라서 "쓰기 API가 2xx를 반환했다면 그 변경은 이미 커밋되어 다음 요청에서 보인다"를 **API 계약**으로 삼는다. 이 계약이 있어야 프론트는 변경 후 재조회라는 평범한 패턴을 그대로 쓸 수 있고, 계층 규약(서비스는 커밋하지 않는다)도 유지된다.

## Considered Options

### 커밋 시점을 어디서 보장할 것인가

- **커밋만 떼어낸 전역 의존성 + `scope="function"` (채택)**: `scope`는 FastAPI가 제공하는 공개 파라미터로, 종료 코드를 *path operation 함수 종료 후, 응답 전송 전*에 실행한다. 커밋을 `commit_unit_of_work`로 분리해 앱 전역 의존성으로 걸면 모든 라우트(fastapi-users 라우터 포함)가 자동으로 적용된다. 세션은 요청당 하나 그대로라 트랜잭션도 하나다. 커밋 실패가 응답 전에 나므로 500으로 정상 전파된다.
- **세션 의존성 자체를 `scope="function"`으로 (기각 — 불가)**: 가장 직관적이지만 FastAPI가 **request 스코프 의존성이 function 스코프 의존성에 의존하는 것을 금지**한다. fastapi-users의 `get_user_db`는 우리가 스코프를 지정할 수 없는 평범한 의존성이라 `DependencyScopeError`로 앱이 뜨지 않는다(실측). 이를 피하려면 인증 체인용 세션과 라우트용 세션을 **둘로 쪼개야** 하는데, 요청당 커넥션이 2배가 되고 한 요청의 쓰기가 두 트랜잭션으로 갈라진다.
- **라우트/서비스에서 명시적으로 `commit()` (기각)**: 시점은 확실하지만 커밋 책임이 요청 스코프에서 서비스·라우트로 흩어진다. ADR-0007의 "라우트는 얇게, 서비스는 커밋하지 않는다"를 깨고, 쓰기 경로마다 커밋 호출을 빠뜨릴 수 있는 표면이 생긴다. 단일 출처(G1) 위반.
- **커스텀 `APIRoute` 클래스에서 커밋 (기각)**: 응답 전송 전이라는 시점은 만족하지만, 세션을 `request.state`에 실어 라우트 핸들러가 꺼내 쓰는 우회가 필요하고 `route_class`를 라우터마다 지정해야 한다(`include_router`는 상위 `route_class`를 하위에 전파하지 않는다). 공개 노브가 있는데 내부 배선을 흉내 내는 셈.
- **프론트에서 재조회 대신 캐시 패치 (기각 — 단독으로는)**: 변경 응답으로 캐시를 직접 갱신하면 그 화면은 고쳐지지만, 백엔드 계약은 여전히 "2xx인데 아직 안 보일 수 있음"이다. 새로 추가되는 모든 쓰기 경로가 같은 함정을 다시 밟고, 커밋 실패 은폐도 남는다. 증상 대응이지 원인 대응이 아니다.

## Consequences

- `app/db/session.py`가 `SessionDep`(= `Annotated[AsyncSession, Depends(get_session)]`)과 `commit_unit_of_work`를 공개하고, `create_app()`이 후자를 앱 전역 의존성으로 건다. 세션을 주입받는 모든 곳(라우트·`core/permissions.py`·`core/users.py`의 fastapi-users 배선)은 `SessionDep` 별칭만 쓴다. `Depends(get_session)`를 직접 쓰는 새 코드는 리뷰에서 결함으로 본다.
- `get_session`은 더 이상 커밋하지 않는다 — 열고/닫고, 에러 시 롤백만 한다. 커밋 책임이 두 곳에 있으면 시점 규약이 다시 흐려진다.
- **백그라운드 태스크에서 이 세션에 쓰기를 이어갈 수 없다.** 응답 전에 이미 커밋되기 때문이다. 그런 작업이 필요하면 자체 세션을 여는 `jobs/` 경로처럼 별도 세션을 만든다(스케줄러는 이미 그렇게 한다).
- 커밋 지연이 응답 시간에 포함된다 — 실측으로 스냅샷 삭제 응답이 약 5ms → 약 34ms가 됐다.
- 그 대가로 2xx가 곧 영속성 보장이 된다.
- 테스트(`conftest`)는 `get_session`을 override 해 한 세션을 공유하므로 이 시점 규약을 재현하지 않는다 — 회귀는 의존성 선언 자체(전역 `commit_unit_of_work` + `scope="function"`)를 검증한다.
