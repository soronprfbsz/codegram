# 편집 리스는 닫을 때 즉시 반납하고, 뺏김은 저장 실패가 아니라 예고·알림으로 전달한다

> **Status**: Proposed · **Tags**: `collaboration` · **Date**: 2026-07-28 · **Supersedes**: — · **Related**: ADR-0015

ADR-0015의 단일 편집자 모델(락 TTL 60초 + 가시성 게이팅 하트비트 20초 + 소유자 강제 회수)은 그대로 둔다. 바꾸는 것은 **리스가 손을 떠나는 방식과, 그 사실을 사용자가 알게 되는 경로**다.

1. **닫을 때는 즉시 반납한다.** `pagehide`에서 리스를 해제한다. 탭 전환(`visibilitychange`)에서는 해제하지 **않는다**.
2. **숨김 상태에서도 하트비트를 유지한다.** 방치된 탭 회수는 만료가 아니라 ①의 명시적 반납이 담당한다.
3. **뺏김은 저장이 실패하기 전에 알린다.** 리스를 잃은 순간(상태 폴링이 감지) 배너로 알리고 "다시 편집하기" 버튼을 준다.

## 문제 (실측, 2026-07-28 로컬 스택)

- **브라우저를 닫아도 리스가 즉시 풀리지 않는다.** `releaseLock`은 `keepalive` fetch로 종료 중에도 나갈 수 있게 만들어져 있는데, 호출부가 React effect cleanup 뿐이다. 탭을 닫으면 언마운트가 일어나지 않고 `pagehide`/`beforeunload` 핸들러도 없다. 실측: 컨텍스트를 닫은 0.3초 뒤에도 `locked=true`, **60.7초** 뒤에야 해제. 남은 사람은 아무 잘못 없이 1분을 기다린다.
- **탭을 잠깐 옮기면 편집 중이던 사람이 조용히 리스를 잃는다.** 하트비트가 `visibilityState === 'visible'`로 게이팅돼 있어, 다른 탭을 60초 보고 오면 만료된다. 실측 재현: A가 75초 숨김 → B가 200으로 획득 → A가 돌아와 타이핑 → 저장 409 → "편집 권한이 넘어갔습니다" 다이얼로그. **A는 잃는 순간을 통보받지 못하고, 저장이 실패하고 나서야 안다.**
- **되찾을 방법이 UI에 없다.** `lease.takeover`와 i18n `editLock.takeover`("편집 이어받기")가 구현돼 있으나 어디에서도 렌더되지 않는다. 사용자에게 남은 선택지는 다이얼로그의 "새로고침"뿐이다.

가시성 게이팅 자체는 ADR-0015가 의도한 것이다("켜둔 채 방치한 탭이 락을 영원히 쥐는 문제를 방지"). 문제는 그것이 **방치된 탭과 잠깐 자리를 비운 편집자를 구분하지 못한다**는 점, 그리고 회수 수단이 만료 하나뿐이라 게이팅을 뺄 수도 없다는 점이다. `pagehide` 반납이 생기면 "방치 탭 회수"라는 게이팅의 존재 이유가 사라지므로, ①이 ②의 전제가 된다.

## Considered Options

### 닫힌 창의 리스를 어떻게 회수하는가

- **`pagehide`에서 명시적 반납 (채택)**: 브라우저·탭을 닫는 순간 DELETE가 나가고 다음 사람은 즉시 편집할 수 있다. `keepalive: true`가 이미 붙어 있어 언로드 중에도 전송된다. bfcache 복귀(`event.persisted`)는 재획득으로 처리한다. 반납이 유실되면 TTL이 그대로 백스톱이라 최악의 경우가 지금과 같다 — 안전한 방향의 변경이다.
- **TTL 단축 (기각)**: 대기 시간은 줄지만 잠깐 자리를 비운 편집자를 **더 자주** 밀어낸다. 지금 문제를 악화시키는 방향이다.
- **서버 측 유휴 감지 (기각)**: 연결 상태를 서버가 알려면 WebSocket/SSE가 필요하다. ADR-0015가 실시간 채널을 도입하지 않기로 한 결정을 뒤집는 비용이 이 문제에 비해 과하다.

### 탭이 숨겨졌을 때 하트비트

- **계속 renew (채택, ①이 선행 조건)**: 다른 탭에서 스펙을 읽고 오는 것은 편집 세션의 일부다. 그 사이 리스를 잃을 이유가 없다. 방치된 탭 회수는 ①의 명시적 반납이 맡고, 그마저 실패하면 TTL이 받는다. **①을 먼저 넣지 않고 게이팅만 풀면 방치 탭이 리스를 영구히 쥔다** — 순서가 중요하다.
- **현행 유지 (기각)**: 사용자가 겪는 현상의 직접 원인이다.
- **숨김 상태에서 하트비트 간격만 늘림 (기각)**: 만료 시점을 미룰 뿐 같은 일이 더 드물게 일어난다. 원인이 아니라 빈도를 건드린다.

### 리스를 잃은 사실을 언제 알리는가

- **잃은 즉시 배너 + "다시 편집하기" (채택)**: 상태 폴링이 이미 15초마다 돌고 있어 감지 지점이 존재한다. 잃은 순간 상단에 "○○ 님이 편집을 이어받았습니다 / 다시 편집하기"를 띄운다. 리스가 비어 있으면 버튼이 바로 재획득하고, 살아 있으면 비활성(소유자는 강제 회수). 이미 있는 `lease.takeover`를 연결한다.
- **저장 실패 다이얼로그만 유지 (기각)**: 현행. 사용자는 이미 잃은 뒤 한참 타이핑한 다음에야 알게 되고, 그 시점엔 되돌릴 것이 쌓여 있다.
- **잃기 전 예고(만료 임박 카운트다운) (기각)**: ②를 채택하면 편집자가 예기치 않게 만료되는 경로가 사라지므로 예고할 대상이 없다. 남는 경로는 소유자의 강제 회수뿐인데, 그것은 즉시 일어나므로 예고할 시간이 없다.

## Consequences

- `useEditLease`가 `pagehide` 리스너를 등록해 `releaseLock`을 호출한다. React unmount 경로(프로젝트 전환)는 그대로 둔다 — 두 경로가 모두 반납을 시도해도 서버의 `release`는 보유자일 때만 지우므로 무해하다.
- 하트비트의 `visibilityState` 조건이 빠진다. 숨겨진 탭도 20초마다 renew하므로 **백그라운드 요청이 늘어난다**(편집자 1명당 20초에 1회). 상태 폴링은 지금처럼 포커스 기반으로 둔다.
- 하트비트는 **보유 중일 때만** renew한다는 현행 조건도 재검토 대상이다 — 한 번 잃으면 자동으로 다시 잡지 않아, 되찾기는 ③의 버튼이나 다음 저장에 의존한다. ③을 넣으면 이 조건은 그대로 두어도 사용자에게 막다른 길이 되지 않는다.
- 새 사용자 노출 문자열(배너·버튼)이 ko/en에 추가된다. 미사용 상태로 남아 있던 `editLock.takeover`가 실제로 쓰이게 된다.
- **회귀 방어**: 이 영역은 지금 `useEditLease` 단위 테스트가 없다(표시용 컴포넌트 테스트 2개뿐). 위 동작은 타이머·가시성·언로드가 얽혀 있어 훅 단위 테스트를 함께 추가한다.
- TTL 60초와 소유자 강제 회수는 그대로다. ADR-0015의 단일 편집자 모델을 대체하지 않는다.
