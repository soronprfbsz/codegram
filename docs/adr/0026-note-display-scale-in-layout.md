# 노트의 표시 크기는 배율 하나로 표현하고 Layout에 저장한다

> **Status**: Accepted · **Tags**: `rendering`, `data-model` · **Date**: 2026-07-31 · **Supersedes**: — · **Related**: ADR-0001, ADR-0004, ADR-0012, ADR-0020

캔버스의 스티키 노트(DBML standalone `Note`)는 사용자가 크기를 조절할 수 있다. 그 크기는 **치수(폭·높이)가 아니라 배율 하나(`scale`)**로 표현하고, `project.layout`(JSONB)의 `positions[nodeId].scale`에 저장한다. DBML 텍스트에는 남기지 않는다.

배율은 카드 전체에 걸린다 — 폰트·패딩·radius·테두리가 같은 비율로 커진다. 즉 **리사이즈가 아니라 줌**이다. 범위는 `1.0 ~ 3.0`이고 `1.0`(=기존 기본 크기)이 하한이다. 축소는 없다.

## 문제

노트는 캔버스에서 유일하게 "내용이 사람 글"인 노드다. 테이블·enum은 행 개수가 크기를 정하지만 노트는 강조하고 싶은 정도가 크기를 정한다 — 도면 한복판의 경고문은 크게, 구석의 메모는 작게. 그런데 지금 노트는 고정 크기이고, 크기를 담을 자리가 어디에도 없다: `StoredLayout`은 `positions`와 `edges`(ADR-0012)뿐이며 둘 다 **좌표**만 다룬다. 크기 축이 처음 들어온다.

동시에 "크기를 키우면 폰트도 커진다"는 요구는 자유 종횡비 리사이즈와 양립하지 않는다. 폰트가 폭을 따라 커지면 넓게 펴도 줄바꿈 여유가 늘지 않고 글자만 커진다. 납작하게 늘리면 글자가 박스를 넘친다. 두 요구 중 하나를 포기해야 한다.

## Considered Options

### 크기를 무엇으로 표현하는가

- **배율 하나 + 콘텐츠 고유 크기 (채택)**: 카드에 명시 치수를 주지 않고, 루트 `font-size`를 `토큰 × scale`로 두고 내부 치수를 전부 `em`으로 표현한다. 폭·높이가 실제 DOM 레이아웃으로 배율만큼 커지므로 React Flow의 `measured`가 정확하고, 엣지 장애물·선택 링·A* 라우팅이 추가 작업 없이 따라온다. 종횡비를 콘텐츠가 정하므로 **글자가 박스를 넘치는 상태가 표현 불가능**하다. 저장값도 숫자 하나다.
- **폭·높이 2개 저장 + 폰트는 파생 (기각)**: 자유 종횡비를 주면 위의 모순이 그대로 드러난다. 폰트를 짧은 변 기준으로 잡아 넘침을 막을 수는 있지만, 그러면 "넓게 늘렸는데 아무 변화도 없는" 조작이 생긴다 — 조작과 결과가 어긋난다. 노트의 고유 폭이 콘텐츠 길이에 따라 다르다는 점도 기준 치수를 자의적으로 만든다.
- **CSS `transform: scale()` (기각)**: 가장 짧은 코드지만 틀린다. React Flow v12는 노드 래퍼의 border-box를 ResizeObserver로 측정하므로 내부 요소의 transform은 `measured`에 반영되지 않는다. 화면상 카드만 커지고 장애물 rect·선택 링·dagre 배치는 원래 크기에 머물러, 관계선이 커진 카드를 통과한다.

### 배율을 어디에 저장하는가

- **`positions` 엔트리 안에 `scale?: number` (채택)**: 배율은 좌표와 키(`note:${name}`)·생명주기·프레임 규칙이 완전히 같다. 같은 엔트리에 두면 ADR-0004의 보존/소실 규칙(rename → 소실 허용, DB 동기화 → 이름 기반 보존)과 고아 정리가 자동으로 승계된다. `version: 1` 유지 — 옵셔널 필드 추가는 하위 호환이고, 기존 프로젝트는 배율 없음 = `1.0`으로 열린다.
- **`StoredLayout` 최상위에 별도 `scales` 맵 (기각)**: `edges`처럼 새 맵을 두는 쪽이 대칭적으로 보이지만, `edges`는 **키 공간이 다르다**(엣지 id). 배율은 노드 id로 키가 같아서, 맵을 나누면 같은 노드에 대한 두 엔트리를 따로 정리·프레임 검사해야 한다. 갈라질 이유 없는 상태를 갈라놓는 비용만 남는다.
- **DBML 텍스트에 남기기 (기각)**: ADR-0001 — DBML은 **구조**의 단일 진실이다. 표시 배율은 구조가 아니라 배치이며, 배치는 layout이 담는다(ADR-0004·0012의 선례). 문법상으로도 불가능하다: `@dbml/core`는 standalone `Note`에 setting list조차 거부한다(실측 — `Note x [headercolor: …]` → `"A Note shouldn't have a setting list"`, code 3006). 커스텀 주석으로 우회하면 내보낸 DBML이 다른 도구에서 의미를 잃는다.
- **저장하지 않기 (기각)**: 새로고침마다 초기화된다. 강조하려고 키운 노트가 다음 사람에게는 안 보인다 — 기능의 목적 자체가 사라진다.

### 하한을 어디에 두는가

- **`1.0` = 기존 기본 크기 (채택)**: 축소를 허용하지 않는다. 노트를 줄이려는 동기는 "도면을 덜 가리기"인데, 그건 글자를 읽을 수 없게 만드는 방식으로 달성된다. 안 읽히는 노트는 노트가 아니다. 가림 문제는 이동으로 해결한다.
- **`0.5` 이하까지 축소 허용 (기각)**: 캔버스 줌아웃 상태에서 노트 글자가 픽셀 뭉치가 된다. 도면에 "무엇인지 알 수 없는 노란 사각형"을 남기는 조작을 굳이 제공할 이유가 없다.

## Consequences

- `StoredPosition`에 `scale?: number`가 추가된다. `nodesToLayout`은 노트의 현재 배율을 함께 써 내려야 한다 — **빠뜨리면 다음 노드 드래그 저장에서 배율이 조용히 소실된다.** 이 왕복이 이 결정의 유일한 취약점이므로 단위 테스트로 고정한다.
- 사용자는 종횡비를 바꿀 수 없다. 노트를 "넓고 납작하게" 만들 방법은 없고, 폭을 바꾸는 유일한 수단은 글을 고치는 것이다.
- Auto-arrange는 배율을 보존한다. 위치를 전면 재계산해도 "이 노트는 크게 보여야 한다"는 의도는 배치와 무관하게 유효하다(ADR-0012에서 auto-arrange가 수동 경로를 **제거**하는 것과 다르다 — 경로는 좌표에 의존하므로 재배치 후 무의미해지지만, 배율은 그렇지 않다).
- 배율은 프로젝트 layout에 저장되므로 **공유 상태**다. 한 사람이 키운 노트는 모두에게 크다. 편집 모드에서만 조절 가능하다(ADR-0025 — 읽기 모드에서는 핸들이 렌더되지 않는다).
- dagre 자동배치가 쓰는 `nodeSize()`는 노트를 `STICKY_WIDTH × scale`, `STICKY_HEIGHT × scale`로 보고해야 한다. 그러지 않으면 커진 노트 주변에 배치 여유가 부족해진다.
- undo는 없다(앱 전반과 일관). 복구 수단은 핸들 더블클릭 → `1.0` 리셋이다.
- 폰트는 `--erd-fs-*` 토큰에 배율을 곱해 표현하므로 raw px가 생기지 않는다(ADR-0020 유지). 신규 토큰은 없다.
