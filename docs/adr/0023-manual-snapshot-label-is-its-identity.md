# 수동 스냅샷의 라벨은 이름표가 아니라 **식별자**다 — 같은 라벨로 저장하면 덮어쓴다

> **Status**: Accepted · **Tags**: `collaboration` · **Date**: 2026-07-28 · **Supersedes**: — · **Related**: ADR-0014

ADR-0014는 수동 스냅샷을 "라벨을 붙여 명시적으로 생성, 중복 허용"으로 정했다. 그 결과 같은 이름으로 여러 번 저장하면 `#1`(7/27), `#1`(7/28)처럼 **이름이 같고 시각만 다른 행이 계속 쌓인다** — 목록에서 어느 것이 최신인지 이름으로는 구분되지 않고, 프로젝트당 50개 상한도 같은 이름의 사본으로 소진된다.

수동 스냅샷의 라벨을 **프로젝트 안에서 그 스냅샷을 가리키는 이름(식별자)**으로 재정의한다. 라벨이 있는 수동 스냅샷을 같은 라벨로 다시 저장하면 새 행을 만들지 않고 **기존 행의 내용을 현재 상태로 갱신**한다(`dbml_text`·`layout`·`content_hash`·작성자·시각). 되돌릴 수 없는 덮어쓰기이므로 **저장 전에 사용자에게 확인**을 받는다.

- **라벨을 비운 저장(무제)은 지금처럼 항상 새로 만든다.** 이름이 없으면 가리킬 대상도 없다. "빠르게 하나 찍어두기"는 그대로 동작한다.
- **자동 스냅샷은 무관하다.** 라벨이 없고 콘텐츠 해시로 중복을 거른다(ADR-0014 그대로).
- 이는 ADR-0014의 "수동은 중복 허용"을 **수동 스냅샷에 한해** 좁히는 연장이다. 2단 보관·prune·원복 설계는 그대로다.

## Considered Options

### 같은 라벨로 저장할 때의 동작

- **확인 후 덮어쓰기 (채택)**: 이름이 곧 식별자라는 모델이 사용자 기대와 맞는다("작업중" 하나를 계속 갱신). 목록이 이름 단위로 유지되고 50개 상한도 이름 수만큼만 쓴다. 되돌릴 수 없으므로 확인 모달을 거친다.
- **묻지 않고 덮어쓰기 (기각)**: 클릭은 적지만 오타 한 번으로 남의(또는 내) 기존 스냅샷이 소리 없이 사라진다. 스냅샷은 복구 수단인데 그 복구 수단을 실수로 날리는 경로를 만들 수 없다.
- **같은 라벨 저장 거부 (기각)**: 데이터는 가장 안전하지만 "덮어쓰고 싶다"는 실제 요구를 해결하지 못한다. 사용자가 지우고 다시 저장하는 2단계를 수동으로 하게 될 뿐이다.
- **현행 유지(중복 허용) (기각)**: 이름이 중복된 목록은 최신 판별을 시각에 의존하게 만들고 상한을 잠식한다.

### 중복을 어디서 판정하는가

- **백엔드 계약: `overwrite` 없으면 409 (채택)**: `POST .../snapshots`가 같은 라벨의 수동 스냅샷을 발견하면 `409 label_exists`를 돌려주고, 프론트는 확인 모달을 띄운 뒤 `overwrite: true`로 재요청한다. 판정이 DB 실제 상태 기준이라 목록 캐시가 낡아도 중복이 새지 않는다. 경로가 하나뿐이다.
- **프론트가 로드된 목록으로 판정 (기각)**: 요청 1회로 끝나지만 판정 근거가 캐시라, 다른 사람이 방금 만든 같은 라벨을 못 보고 중복을 만든다. 협업(ADR-0015) 전제와 맞지 않는다.

### 덮어쓴 행의 `created_at`

- **현재 시각으로 갱신 (채택)**: 그 행의 의미가 "이 이름의 최신 저장본"이므로 표시되는 시각도 최신이어야 하고, 최신순 목록에서 위로 올라와야 한다.
- **최초 생성 시각 유지 (기각)**: 내용은 방금 것인데 시각은 옛날로 보여 목록이 거짓말을 한다.

## Consequences

- `project_snapshot` 행은 더 이상 write-once가 아니다 — **수동 스냅샷에 한해** 같은 라벨 재저장으로 내용이 갱신된다(모델 docstring 갱신). `id`는 유지되므로 미리보기/원복 링크가 깨지지 않는다.
- `ProjectSnapshotCreate`에 `overwrite: bool = False`가 추가되고, 생성 엔드포인트가 `409 {"reason": "label_exists"}`를 반환할 수 있다.
- **DB 레벨 유니크 제약은 두지 않는다.** 이 결정 이전에 만들어진 같은 라벨의 중복 행이 이미 존재하고(사용자 데이터), 제약을 걸려면 그것들을 지우거나 이름을 바꿔야 한다. 판정은 서비스에서 하고, 기존 중복이 있으면 **가장 최근 행**을 갱신 대상으로 삼는다. 남은 옛 중복은 사용자가 직접 삭제한다.
- 라벨 비교는 **양끝 공백을 제거한 문자열의 정확한 일치**다(대소문자 구분). 프론트도 저장 시 같은 방식으로 다듬어 보낸다.
