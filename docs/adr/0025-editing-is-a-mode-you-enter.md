# 편집은 들어가는 모드다 — 프로젝트를 열면 언제나 읽기 전용으로 시작한다

> **Status**: Accepted · **Tags**: `collaboration` · **Date**: 2026-07-29 · **Supersedes**: — · **Related**: ADR-0015, ADR-0024

ADR-0015는 "편집자(소유자 포함)가 **에디터를 열면** 프로젝트 단위 편집 락을 잡는다"고 정했다. 이 획득 시점을 바꾼다: **프로젝트를 여는 것만으로는 리스를 잡지 않는다.** 편집 권한이 있는 사람도 언제나 읽기 전용으로 들어오고, 탑바의 **편집 모드** 버튼을 눌러 명시적으로 진입할 때만 리스를 잡는다. 나가면 즉시 반납한다.

단일 편집자 모델·TTL 60초·소유자 강제 회수(ADR-0015)와 닫을 때 즉시 반납·상실 즉시 알림(ADR-0024)은 그대로다. 바뀌는 것은 **리스를 잡는 계기**뿐이다.

## 문제

열기만 해도 리스를 잡으니, **보러 들어온 사람이 편집자를 밀어낸다.** ERD를 확인만 하려고 프로젝트를 연 사람이 자동으로 편집권을 쥐고, 실제로 고치려던 사람은 "○○ 님이 편집 중"에 막힌다. 본인은 자기가 무엇을 점유했는지 모른다 — 아무것도 편집하지 않았기 때문이다.

ADR-0024가 그 부작용을 줄이긴 했다(닫으면 즉시 반납). 하지만 탭을 열어둔 채 다른 일을 하는 것은 흔하고, 그 사이 리스는 계속 그 사람 것이다. 회수 수단은 소유자의 강제 이어받기뿐이다.

근본 원인은 **의도를 추론한 것**이다. "에디터를 열었다"에서 "편집할 것이다"를 유도했는데, 이 도구에서 열기는 대부분 읽기다. 추론을 걷어내고 사용자가 직접 말하게 한다.

## Considered Options

### 리스를 언제 잡는가

- **명시적 편집 모드 진입 (채택)**: 사용자가 "편집하겠다"고 말할 때만 잡는다. 점유가 의도와 일치하므로 "누가 왜 잡고 있는지"가 언제나 설명 가능하다. 읽기만 하는 다수가 편집자를 막지 않는다. 대가는 실제로 편집할 때의 클릭 한 번이다.
- **열면 자동 획득 (기각 — 현행)**: 편집자에겐 클릭이 없지만, 읽기 목적 열람이 편집을 막는 비용을 전원이 나눠 낸다. 위 문제의 직접 원인.
- **첫 편집 시도에 자동 획득 (기각)**: 클릭이 없고 점유도 의도와 맞지만, 키를 누른 뒤에야 "다른 사람이 편집 중입니다"를 만나게 된다. 이미 친 글자를 어떻게 할지가 남고, ADR-0024가 없애려던 "저장 실패로 알게 되는" 경험으로 되돌아간다. 편집 가능 여부는 **타이핑 전에** 화면에 드러나야 한다.
- **혼자인 프로젝트만 자동 획득 (기각)**: 흔한 경우의 클릭을 없애지만 규칙이 상태에 따라 달라진다("어떤 프로젝트는 바로 써지고 어떤 건 아니다"). 멤버가 추가되는 순간 조용히 동작이 바뀌는 것도 나쁘다. 예측 가능성을 택한다.

### 편집 모드에서 나가는 방법

- **명시적 종료 + 이탈 시 자동 반납 (채택)**: 탑바 버튼으로 나가면 즉시 반납한다. 프로젝트 전환·탭 닫기는 ADR-0024의 경로가 그대로 반납한다. 리스 상실(강제 회수·만료)도 편집 모드를 자동 해제한다 — 편집할 수 없는데 편집 모드로 남아 있으면 거짓말이다.
- **자동 종료(유휴 타임아웃) (기각)**: 방치된 편집 모드를 회수하지만, ADR-0015가 활동 기반 만료를 기각한 이유(생각 중인 편집자를 밀어냄)가 그대로 적용된다. TTL 60초가 이미 백스톱이다.

### 모드를 세션에 기억할 것인가

- **기억하지 않는다 (채택)**: 새로고침·재진입은 언제나 읽기 전용이다. "열면 읽기"라는 한 문장이 예외 없이 성립해야 한다.
- **세션에 저장 (기각)**: 클릭을 아끼지만 "어제 편집 모드였으니 오늘도"라는 추론이 다시 들어온다. 방금 걷어낸 것이다.

### 백엔드 계약

- **그대로 둔다 (채택)**: 콘텐츠 쓰기(`take_or_conflict`)는 지금처럼 free/own/expired면 리스를 잡는다. 편집 모드는 **클라이언트의 의도 표현**이지 새 권한 계층이 아니다. 서버 쪽 상호배제(ADR-0015 + 원자적 획득)가 여전히 정답의 출처다. 프론트가 편집 모드 밖에서 쓰기를 보내지 않으므로 실질적으로 문제되지 않고, 만에 하나 보내더라도 리스가 남의 것이면 여전히 409다.
- **편집 모드 전용 API 추가 (기각)**: 서버에 상태를 하나 더 만들지만 리스가 이미 그 상태다. 중복.

## Consequences

- `useEditLease`가 마운트 시 acquire하지 않는다. `editMode` 상태가 생기고 `enterEditMode()`/`exitEditMode()`가 리스를 잡고 놓는다. 하트비트는 편집 모드일 때만 돈다.
- `readOnly`가 `!canEdit || !editMode || 뺏김 || 남이 보유`로 넓어진다. DBML 에디터·캔버스 드래그·정보 패널 구조 편집·가져오기 메뉴가 전부 이 값을 이미 보고 있으므로(직전 커밋) 편집 모드 밖에서는 자동으로 잠긴다.
- 탑바 락 표시기가 **모드 스위치**가 된다: 읽기 전용일 때 "편집 모드", 편집 중일 때 "편집 종료". 남이 잡고 있으면 진입 버튼은 비활성이고 소유자는 강제 이어받기를 쓴다.
- **편집자는 매 세션 클릭 한 번을 더 낸다.** 특히 혼자 쓰는 프로젝트에서 순수 비용이다. 읽기 목적 열람이 편집을 막지 않는 대가로 받아들인다. 실사용에서 거슬리면 "혼자인 프로젝트 자동 진입"이 아니라, 편집 모드 진입을 첫 편집 제스처에 붙이는 쪽(위 기각안)을 다시 검토한다 — 그때는 "타이핑 전에 드러난다"를 어떻게 지킬지가 관건이다.
- 뷰어는 달라지는 것이 없다 — 애초에 진입 버튼이 없다.
